# Bot Profile & Thought Bubble — Design Specification

Status: design, not implemented.
Scope: per-session bot avatar profile, the avatar picker, the repeating "unsolicited thought" cycle, the raw-transcript advice call, and the cartoon thought bubble (including all animation and lifecycle rules).

This document is normative. It uses MUST / MUST NOT / SHOULD with their usual meanings. Numbers, selectors, timings and field names are part of the design and must be implemented as written unless this document is amended.

---

## 0. Summary

Each chat session has its own bot avatar. The avatar lives in the top-left header. Clicking it opens a picker; choosing a bot sets that session's profile. The bot has a personality; after a random number of messages it produces one short, unsolicited thought, generated from the raw (unsummarised) transcript since its previous thought, using the same model as the main agent at low thinking. The thought appears as a plush cartoon thought bubble attached to the avatar, is user-facing only, lasts five minutes, and can be dismissed.

---

## 1. Vocabulary

- **Profile / bot**: the avatar selected for one session. One of eight types: `clover`, `flower`, `star`, `ghost`, `mech`, `circle`, `hexagon`, `square`.
- **Personality**: the character, tone and unsolicited-advice style mapped to a bot (Section 4).
- **Thought / advice**: the short text generated by the advice call and shown in the thought bubble.
- **Cycle**: one interval from a starting message count to the next thought.
- **`x`**: the cycle length in "messages", an integer rolled uniformly in `[150, 300]`.
- **Counter**: the session's message count exactly as the session tile shows it (Section 5.1).
- **Window**: the raw transcript between the previous thought (or session start for the first) and the current thought (Section 6).
- **Bubble**: the cartoon thought cloud (Section 10).

---

## 2. Hard invariants

1. The bubble and its text MUST NOT be written into `main/*.jsonl`, MUST NOT be sent to the main agent, and MUST NOT appear in the main agent's prompt, view, tree or compaction input.
2. The bubble MUST NOT change the session's counter (it writes nothing to `main/` or `main.index`).
3. The bubble MUST NOT be counted as a "message" anywhere.
4. The advice call MUST NOT run with tools, MUST NOT create or modify files, and MUST NOT be given the compactor's summaries or the view.
5. The profile MUST be per session; there is no global profile.
6. The bubble is scoped to one session and one tab set; it must never appear over a different session.
7. The five-minute life is measured from the thought's creation time, not from when it becomes visible.
8. All timings assume `prefers-reduced-motion: no-preference` unless Section 11.6 applies.

## 3. The avatar in the header

### 3.1 Current state

The header brand is a single `<button class="brand" data-go="/">` containing `<span id="fx-brand">` (a React island rendering `BotAvatar`) and the text `Uniichat`. `BrandIsland` renders `<BotAvatar type="clover" state={busy ? "working" : "default"} size={30} shading="fabric" />`.

### 3.2 Required structure

The brand MUST split into two independent controls:

- **Avatar button** — wraps only the avatar; `aria-label="Choose this chat's bot"`; opens the picker. It MUST NOT navigate.
- **Wordmark link** — the text `Uniichat`; keeps the current behaviour (go home), `data-go="/"`.

The avatar button is 30×30 (the avatar itself stays `size={30}`), with a 4 px padding hit area (38×38 button), no visible chrome at rest.

### 3.3 Avatar rendering

- The avatar MUST render the session's selected bot: `<BotAvatar type={profile} state={busy ? "working" : "default"} size={30} shading="fabric" />`.
- `busy` keeps its current meaning (main agent generating); state switching is otherwise unchanged.
- Changing session MUST re-render the avatar to that session's profile before any other state change is visible.
- A session with no stored profile MUST show `clover`.

### 3.4 Header affordance

- Hover on the avatar: the bot gets a 1.06 scale over 180 ms and a soft plush shadow; cursor `pointer`.
- Focus-visible: a 2 px ring in the avatar's own accent at 2 px offset.
- Press: scale 0.96 for 90 ms.
- No text label is added next to the avatar.

## 4. Personalities

Each bot has a personality object. The personalities are data, not code branches; the advice prompt is assembled from the fields.

Fields per personality:

- `name` — the bot's character name.
- `archetype` — one line.
- `tone` — how it speaks.
- `attention` — what it notices in the transcript.
- `offer` — the kind of unsolicited thing it gives.
- `prompt` — a sentence or two injected into the system prompt.
- `palette` — bubble colours (Section 10.3).

## 5. The cycle

### 5.1 The counter (defined exactly)

The session tile's count is:

```ts
messages = Math.floor(stat(dir + "/main.index").size / SLOT)   // SLOT = 16
```

This is `Sessions.Info.messages`. The bot MUST use exactly this formula, reading the same file, at the same moments. It is not a literal count of JSONL lines.

### 5.2 State machine

Per-session bot state (persisted in the session's `view.json`, Section 13):

```
{
  avatar: string,           // one of the eight
  due: number | null,       // counter value at which the next thought is due
  base: number | null,      // counter value at the moment the previous thought was generated
  from: number | null,      // highest main-log message index included in the previous window
  at: number | null,        // ms epoch when the previous thought was generated
  pending: { text, at } | null
}
```

Initial state for a session: `{ avatar: "clover", due: null, base: null, from: null, at: null, pending: null }`.

### 5.3 First user message

When the session's **first user message** is accepted and logged:

1. Read the counter `c`.
2. Roll `x` uniformly in `[150, 300]`.
3. Set `base = c`, `due = c + x`, `from = <highest main-log index before this message>`, `at = null`.
4. Do not generate anything.

"First user message" means: no user-kind entry in the session's main transcript before this one. The synthetic welcome/sign-in lines do not count as user messages.

### 5.4 Trigger check (on every later user message)

After the user's new message is accepted and logged (i.e. `main.index` has been updated), and **before scheduling the main agent's request**:

1. Read the counter `c`.
2. If `due !== null && c >= due` → fire the advice (Section 7).
3. Otherwise do nothing.

The check runs once per user message, at turn start. It never runs mid-turn while the agent is generating. If the counter crosses `due` because of tool output, the thought fires on the user's next message.

### 5.5 After a successful thought

On success (Section 7.4), when the thought is generated at counter `c_fire`:

1. Set `base = c_fire`, `at = now`, `from = <highest main-log index at this moment>`, `due = null`.
2. Set `pending = { text, at: now }`.
3. Show/broadcast the bubble (Section 12).
4. On the user's **next** message: roll a new `x`, set `due = base + x`, `pending` unchanged (expiry still applies). This restarts the cycle.

On failure: leave `due` unchanged so the advice is retried at the next user message; do not advance `from`/`base`/`at`; no bubble.

### 5.6 Why `base` and not the live counter

`base` is the count at the moment the thought was generated. Tool messages produced after the thought (same turn) are therefore included in the next cycle; the new `x` counts from the advice moment, as specified.

### 5.7 Cycle edge cases

- **Mid-turn crossing:** never fires mid-turn; waits for the next user message.
- **Multiple crossings in one turn:** still one thought at the next user message.
- **User sends nothing for a long time:** no new cycle starts; `pending` expiry still applies.
- **The advice is generated while `due` was already met by a huge jump:** still one thought; the new cycle starts on the next user message.
- **First message in an imported/moved session with existing history:** `base` is the count at that message; `from` is the index before that message (no retroactive window).
- **Archived session:** no checks; on restore, checks resume at the next user message.
- **Deleted session:** state dies with the session.

## 6. The raw window

### 6.1 Definition

The window for a thought is every **raw, unsummarised** message in the session's main transcript whose message index is:

- strictly greater than `from` (the marker stored by the previous thought), or
- for the first thought, all entries from the first user message onward (the synthetic welcome/sign-in lines are excluded).

The window ends at the highest logged message index at the moment the advice is generated. It is **not** "since the last main-model prompt", not a summary, and not the view.

### 6.2 Source

- Files: `~/.unii/users/<user>/sessions/<session>/main/<YYYY-MM-DD>.jsonl`, all day files of that session, concatenated in message-index order.
- Entries carry `i` (message index), `kind`, `text`, `date`, and possibly `size`, `images`.
- Kinds and how they are rendered in the window:
  - `user` → `user: <text>` (MUST be included).
  - `unii` → `assistant: <text>`.
  - `tool` → `tool call: <text>` (the tool name + input JSON as logged).
  - `echo` → `tool result: <text>`.
  - `note` → `note: <text>`.
  - Any other logged kind → `<kind>: <text>`.
- Synthetic welcome/sign-in lines (the session's hello, signed-in line) are excluded for the first window; they are not conversation.
- Images are represented as `[image]` in place; image bytes are never sent.
- The bubble text is not in this window (it is not logged to `main/`).

### 6.3 Building the transcript text

One line per message, oldest first:

```
<i> <role>: <text>
```

where `role` is `user`, `assistant`, `tool call`, `tool result`, `note`, or the raw kind. Multi-line text is preserved; blank lines inside a message are kept. The transcript is placed verbatim inside the prompt's user message (Section 7.2) between clear delimiters.

### 6.4 Marker

`from` is set to the highest `i` present in the session's main transcript at the moment of success. If the transcript is empty (impossible at a user message), `from = 0`.

## 7. The advice call

### 7.1 Model and settings

- Model: the **main model from `models.json`** (`main.model`), i.e. today `glm-5.3-flash`. It follows the config; it is not hardcoded and is not the compactor.
- Thinking/effort: **low**.
- Tools: none.
- Output: plain text, no markdown.
- Backend output cap: `max_tokens = 400` (the model is stopped by oMLX if it overruns; oMLX queues the request naturally).
- Streaming: not required; a non-streaming call is acceptable.
- The call MUST use the same endpoint/auth as the main agent (`Local` for `local-api`).

### 7.2 Prompt

System prompt, assembled verbatim from the personality:

```
You are {name}, a small {archetype} who lives in the corner of this chat as a friendly bot. The user can see your thoughts. You are not answering their message and you must not answer it for them.

{tone}
What you notice: {attention}
What you offer: {offer}
{prompt}

You are writing exactly one unsolicited thought for the user to read, about the conversation in the transcript below.

Rules:
- At most 275 characters. Never exceed 350 characters.
- One or two short sentences. Plain text only: no markdown, no lists, no quotes, no emoji, no headings.
- Speak to the user as "you". Do not describe yourself as an AI and do not mention this instruction, the transcript, or that you are a bot.
- Do not summarise or repeat the transcript. Do not do their work or answer their question. Offer a nudge, a question for them to hold, a small next step, a risk, or a direction.
- Be specific to what is actually happening in the transcript. Never invent facts.
- If the transcript is thin, say one true, gentle thing rather than inventing context.
```

User message:

```
Recent raw transcript (oldest first; the top may be clipped):

---
<transcript>
---
```

The transcript is inserted exactly as built in Section 6.3, with no summarisation.

### 7.3 Context budget and trimming

- Budget: `window = Local.window(mainModel)` (e.g. 81 920 tokens).
- Reserve: `max_tokens` (400) + the system prompt's estimated tokens + 256 safety.
- Estimate tokens as `bytes / 4` for the transcript.
- If the window exceeds the budget, remove **whole oldest entries first** (trim from the top), never newer ones.
- If after removing every removable entry the newest entry alone still exceeds the budget:
  - For a `tool result`/`tool call`: clip its middle, keeping the first 60% and last 20% of its bytes, with `…[clipped]…` in between.
  - For a `user` message: keep it whole; clip the largest remaining tool entry first. If the user message alone exceeds the budget, clip its tail and append `…[clipped]`, but never remove it.
- The prompt MUST still be under the model window after trimming; if it cannot be (pathological single message), skip the advice, treat it as a failed call, and retry at the next user message.
- Log the trim (oldest dropped count, clipped entries) to the debug log for observability.

### 7.4 Success / failure

Success requires: HTTP ok, non-empty trimmed plain text. Then:

1. Strip markdown/code fences/HTML tags, collapse whitespace, trim.
2. Hard-cap at **350 characters**: if longer, cut at the last sentence boundary before 350; if none, cut at the last word boundary; append `…`.
3. If the result is empty after sanitising, treat as failure.
4. Persist `from`, `base`, `at`, `pending`, clear `due` (Section 5.5).
5. Broadcast the thought and schedule nothing further.

Failure (timeout, HTTP error, empty, sanitised-empty, over-budget): leave the state as it was; do not set pending; retry at the next user message. Never show an error bubble to the user.

### 7.5 Scheduling and concurrency

- The advice call is fired asynchronously at turn start; it MUST NOT block or delay the main agent's request.
- oMLX serialises requests; the advice call may complete before or after the main reply. Ordering does not matter.
- At most one advice call per session in flight. If a call is in flight and the user sends another message, do not start a second; the cycle is single-threaded.
- If the session is closed or the server restarts mid-call, the result is discarded; no state is advanced.

### 7.6 What the advice call must never do

- No tools, no file writes, no session changes.
- No access to the compactor's summaries, the view, or the tree.
- No inclusion in the main agent's context, ever.
- No user-visible errors.

## 8. The picker

### 8.1 Opening

- Click/press Enter on the avatar button opens the picker for **that** session.
- Opening does not navigate.
- The picker is a popover (not a page, not a route), anchored under the avatar button.

### 8.2 Anatomy

- Panel: width 300–320 px; site glass styling (hairline border, `--lift` at 94%, 18 px radius, `--shadow-lg`, blurred backdrop); padding 14–16 px.
- Header: `your bot` (uppercase, 9 px, letter-spacing .14em, `--mid`), then the current session's title (11 px, `--ink`, ellipsis, one line).
- Grid: 8 tiles, 4 columns × 2 rows (or 2 × 4 at narrow widths).
- Tile: avatar (`BotAvatar` size 40, `shading="fabric"`, `state="default"`), name below (9 px uppercase, `--soft`); padding 10; radius 12; transparent at rest; selected: 1 px accent border in the bot's accent, tinted background 6%, name `--ink`, a tiny check in the corner.
- Hover: tile background `--hover`, avatar scale 1.06, 160 ms.
- Footer (optional, only if needed): a one-line `each chat picks its own` hint, 9 px `--soft`.
- Close: outside click, `Escape`, or choosing a bot.

### 8.3 Choosing

- Choosing a bot saves `bot.avatar` for the session immediately, updates the header avatar with the same 160 ms cross-fade the avatar uses, closes the picker, and plays the existing `open` sound.
- The set is exactly: `clover, flower, star, ghost, mech, circle, hexagon, square`.
- Clicking the already-selected bot just closes.

### 8.4 State and edge cases

- The picker is bound to the session that was active when it opened. If the session changes while it is open (rail click, palette, device switch), the picker MUST close immediately; it must never write to the newly active session.
- Two tabs on the same session: a choice in one tab updates the other via the state broadcast (the header avatar re-renders).
- A choice on a session that is closing/archived: the write is rejected; the picker closes.
- A session with no stored avatar shows `clover` selected.
- Keyboard: `Tab` moves across tiles; `Enter`/`Space` chooses; `Escape` closes; focus returns to the avatar button; the popover traps focus while open.
- The picker is above the bubble, the meter and the skull (z-index above all three) and below any confirm dialog.
- Accessibility: `role="dialog" aria-label="Choose this chat's bot"`; the current tile has `aria-checked="true"` in a `role="listbox"`.

## 9. The bubble's data flow

1. Turn start (user message accepted) → trigger check (Section 5.4).
2. Due → advice call (Section 7) → success → state write (Section 5.5) → broadcast `thought` to the session.
3. The client on that session: if the bubble is not already visible, show it (Section 10); start/refresh the 5-minute timer.
4. Client not on that session: the server keeps `pending` in `view.json`; when a client joins/returns to the session within 5 minutes, it is sent and shown; after 5 minutes the pending is cleared and never shows.
5. Dismiss: client sends `thought-close`; server clears `pending`; broadcasts close to all tabs of the session; the client fades out.
6. Expiry: client timer fires at `at + 300 000`; fades out; tells the server to clear `pending`; other tabs hide it.
7. New thought while one is visible: the old fades out (fast, 180 ms) and the new forms in; the timer restarts from the new `at`.

## 10. The thought bubble

### 10.1 Where it lives

- Anchored to the top-left avatar button, not in the message flow.
- DOM: a single element per session (`#thought`), `position: fixed`, z-index 60 (above the header, chat, meter and skull; below the picker and confirm dialogs).
- It is not inside `#log`, not a chat row, and does not scroll with the chat.
- If the viewport is narrower than 1350 px (skull hidden), the anchor is unchanged; only the clamping rules change.

### 10.2 Position

- Anchor rectangle = the avatar button's `getBoundingClientRect()`.
- Preferred placement: **above** the avatar, horizontally starting near the avatar's left, tail pointing **down** to the avatar.
- If `avatar.top < bubbleHeight + 16`, place **below** the avatar, tail pointing **up** to it (the avatar is at the top edge, so below is the normal case at desktop sizes).
- Horizontal: `left = clamp(avatar.left - 8, 12, innerWidth - bubbleWidth - 12)`.
- Vertical: 8 px gap between the tail tip and the avatar.
- The bubble repositions on resize and on header scroll (the header is fixed); it never overlaps the picker.
- Tail dots point at the avatar's centre (the dot chain is offset horizontally to sit under/over the avatar).

### 10.3 Form (plush cartoon cloud)

- Shape: a cloud built from the bubble body plus two/three overlapping lobes (pseudo-elements), all with the same plush fill; **not** a plain rounded rectangle.
- Fill: radial gradient from the palette's `Fill light` at 32% 28% to `Fill deep` at the edges; a soft inner highlight at the top-left; a 1 px inner light rim (white at 18%) and a 1.5 px darker outer edge of `Fill deep` at 35% opacity.
- Shadow: `0 10px 30px rgb(0 0 0 / 28%)`, plus a tiny contact shadow.
- Tail: three dots below/above the body, sizes 10, 6.5, 4 px, gaps 5 px, same fill, the smallest nearest the avatar; the chain is 22–28 px long.
- Text: `font: 500 13px/1.5 ui-rounded, "SF Pro Rounded", var(--sans)`; color = palette `Ink`; letter-spacing `-0.01em`; max-width 280 px; wrapping; no ellipsis (text is ≤350 chars); centered vertically with 16 px padding (18 px horizontal).
- Max width 300 px; min width 180 px; max height none (text is short).
- The bubble has `pointer-events: auto`; everything outside it is click-through.
- The bubble is not a button and does not focus-trap.

### 10.4 The close control

- A 18 px circular badge at the bubble's top-right, offset 7 px outside the body, fill `Ink` at 12% with `Ink` at 70% glyph; hover fill 20%, glyph 100%, scale 1.08 (140 ms); press scale 0.92.
- Glyph: a simple × drawn with two 1.25 px strokes, rounded caps.
- `aria-label="Dismiss thought"`, `title` same, focusable, keyboard-activatable (Enter/Space).
- On click: start the exit animation immediately (Section 11.3); the timer is cancelled.
- The badge uses the plush style (soft circle, no hairline border, no site chrome).

### 10.5 Content rules

- The text is plain text; no markdown is rendered (the server sanitises).
- No avatar name, no timestamp, no "thought" label, no icon other than the tail — the cloud itself is the affordance.
- The text is never truncated with an ellipsis by the UI (the server already caps it).

### 10.6 Accessibility

- `role="status"`, `aria-live="polite"`, `aria-atomic="true"`; the text is announced once on show.
- The close button is reachable with `Tab`; `Escape` while the bubble has focus closes it.
- The bubble does not steal focus on show.
- `prefers-reduced-motion` (Section 11.6).

## 11. Animation

All animation is CSS keyframes/transitions on the bubble and its children; the client only toggles classes/states. `prefers-reduced-motion` overrides at 11.6.

### 11.1 Forming in (560 ms)

- Cloud: `scale(0.62) translateY(10px)` → `scale(1) translateY(0)`; easing `cubic-bezier(0.34, 1.56, 0.64, 1)`; opacity 0 → 1 over the first 220 ms.
- Lobes: same transform, 40 ms stagger, `scale(0.4)` start.
- Tail dots: `scale(0)` → `scale(1)`, 40 ms stagger, 220 ms each, overshoot 1.15.
- Text: opacity 0 → 1, `translateY(4px)` → 0, 120 ms delay, 260 ms.
- Highlight sweep: a 700 ms one-shot diagonal highlight across the top-left lobe (opacity .35 → 0), `ease-out`.

### 11.2 Idle (infinite, very subtle)

- Body: `breathe 5.2s ease-in-out infinite` — `scale(1)` → `scale(1.012)` → `scale(1)`.
- Whole bubble: `float 6s ease-in-out infinite` — `translateY(0)` → `-2px` → `0`.
- Tail dots: `bob 2.8s ease-in-out infinite` with 200 ms stagger, ±1.5 px.
- No other movement; the text does not animate in idle.

### 11.3 Fading out (380 ms)

- Tail dots shrink first: `scale(1)` → `scale(0)`, 30 ms stagger, 160 ms.
- Cloud: `scale(1)` → `scale(0.94)`, `translateY(0)` → `4px`, opacity 1 → 0, 220 ms, easing `cubic-bezier(0.4, 0, 0.2, 1)`, 120 ms delay.
- The element is removed after 400 ms.
- Used for both the × and the 5-minute expiry.

### 11.4 Replacing a visible bubble

- Old bubble exit 180 ms (dots 60 ms), no delay; new bubble entrance starts 160 ms after the old fade begins.
- The 5-minute timer restarts at the new `at`.

### 11.5 Close button

- Hover: scale 1.08, fill +8%, 140 ms ease.
- Press: scale 0.92, 90 ms.
- Focus-visible: 1.5 px ring in `Ink` at 2 px offset.

### 11.6 Reduced motion

- Entrance: opacity only, 150 ms.
- Exit: opacity only, 150 ms.
- Idle: none.
- Tail dots: no stagger, no scale overshoot.

## 12. Lifecycle and delivery

### 12.1 Creation time

`at` is set when the advice is generated (server clock). The five minutes run from `at`, regardless of whether the user is looking.

### 12.2 Pending

- The server stores `pending = { text, at }` in the session's `view.json` and broadcasts `{ $: "thought", text, at }` to the session's sockets.
- A client joining that session receives the pending thought only if `now < at + 300 000`; if it is expired, the server clears it and sends nothing.
- If no client is connected, the pending remains until the 5-minute expiry (lazily cleared) or until a client joins within the window.

### 12.3 Visible

- Shown once per pending thought per tab. A reload before expiry re-shows the same text (from `pending`), with the remaining time.
- One bubble per session at a time; a new one replaces the old.
- The bubble does not persist beyond its 5 minutes under any circumstance.

### 12.4 Dismiss and expiry

- Dismiss (`×` or `Escape` with focus): fade out (11.3), clear `pending`, broadcast `thought-close`; other tabs hide it; it never returns.
- Expiry (client timer at `at + 300 000`): same fade, clear `pending`, broadcast; the server also clears expired pending on join/state.
- If the client is offline at expiry, the server's lazy expiry prevents a stale show later.

### 12.5 Session switching

- Switching away does not cancel the timer.
- Switching back before expiry shows the bubble again with the remaining time (re-entrance animation is the 11.1 forming-in, shortened to 300 ms).
- Switching back after expiry shows nothing.
- A bubble for session A must never render while session B is active, even for a frame: the client checks the session id before showing; the element is destroyed on switch.

### 12.6 Multiple tabs

- All tabs of the same session can show the bubble; the first tab's timer and the server pending are the source of truth.
- Dismiss/expiry in one tab broadcasts and hides it in the others.
- Tabs on different sessions are independent.

## 13. Persistence

### 13.1 Where

Per session, in the session directory: `~/.unii/users/<user>/sessions/<session>/view.json`, under the key `bot`:

```json
"bot": {
  "avatar": "clover",
  "due": 1234,
  "base": 1180,
  "from": 50817,
  "at": 1763845000000,
  "pending": { "text": "…", "at": 1763845000000 }
}
```

- Missing/invalid fields fall back to the defaults in 5.2.
- Unknown `avatar` → `clover`.
- `pending` text is capped at 350 characters on write.
- The bubble text is never written anywhere else.

### 13.2 Reads/writes

- The server owns the state; clients never write `view.json` directly. Actions: `bot-avatar` (set avatar), `thought-close` (clear pending).
- Writes are atomic with the existing view save.
- The state is read on turn start (trigger), on join (pending delivery), on avatar render, and on the picker open.

### 13.3 Migration

- Sessions created before this feature have no `bot` key: default avatar `clover`, `due = null`; the first user message after the feature ships initialises the cycle.
- No backfill of old sessions' counters is needed beyond the normal first-message initialisation.

## 14. Server/UI architecture (normative outline)

- **Counter**: reuse `Sessions.Info.messages` (the `main.index` size / 16) — no second definition anywhere.
- **Trigger**: in the server's user-message acceptance path (the same place the user message is logged and the turn is scheduled), synchronously read the counter, run the state machine, and when due spawn the advice job asynchronously. The job must not be awaited by the turn.
- **Raw window**: a server function that reads the session's `main/*.jsonl`, filters `i > from`, maps kinds, builds the line-based transcript, and returns `{ text, from }`.
- **Advice call**: a direct main-model call (same Local auth/model as the agent), effort low, no tools, max_tokens 400, system + user messages as in 7.2; sanitise and cap.
- **State**: in `view.json` `bot`; writes go through the session's view save.
- **Broadcast**: `{ $: "thought", text, at }` to the session's sockets; `{ $: "thought-close" }`; the picker state flows through the existing state broadcast.
- **Client**: the avatar button opens the picker; the picker sends the bot-avatar action; the header avatar renders `bot.avatar`; the bubble is a fixed element with the lifecycle/animations above.
- **No main-context impact**: nothing in this feature touches `main/*.jsonl`, `main.index`, the view, the tree, or the agent's prompt.

## 15. Edge cases (exhaustive list)

1. First message of a brand-new session → roll `x`, no thought.
2. Session with prior history but no bot state (old or imported) → same initialisation at the first new user message.
3. Counter crosses `due` mid-turn via tool output → thought waits for the next user message.
4. Counter jumps past `due` by a large tool output at turn start → one thought, then the cycle restarts on the next user message.
5. User sends several messages quickly → one thought per due crossing; only one advice call in flight.
6. Main agent still generating when the advice call finishes → bubble shows independently; no interaction with the main turn.
7. Advice fails (timeout/HTTP/empty/sanitised-empty) → no bubble; retry at the next user message with the same `due`.
8. Raw window too big → trim oldest whole messages first; clip oversized tool entries; never drop the newest user message; if impossible, skip and retry.
9. Raw window thin (e.g. one short message) → prompt still asks for one true, gentle thought; model may return a short one; no retry on thinness.
10. Session switched while the picker is open → picker closes; no cross-session write.
11. Session switched while the advice is in flight → result stored as pending for its session; shown on return within 5 minutes, else discarded.
12. Two tabs, same session → both show; dismiss/expiry syncs.
13. Two tabs, different sessions → independent.
14. Reload within 5 minutes → pending re-shown with the remaining time.
15. Reload after expiry → nothing.
16. Archived session with a pending bubble → pending cleared on archive; no bubble.
17. Deleted session → state gone.
18. Server restart → pending is read from `view.json`; an in-flight advice is lost; `due` unchanged (retry next message).
19. Advice text over 350 → cut at sentence/word boundary; never show an ellipsis mid-word.
20. Advice call returns markdown/lists → stripped to plain text.
21. Model window changes in `models.json` → trimming adapts via `Local.window`.
22. The main model changes in `models.json` → the advice follows it automatically.
23. oMLX busy → the advice queues; the main reply is never delayed by the feature.
24. Viewport narrow (<1350) → no skull; the bubble still anchors to the avatar and clamps to 12 px margins.
25. Viewport very short → below-placement; the bubble never clips above the header.
26. Reduced motion → opacity-only.
27. Token estimate under-counts (code-heavy transcript) → the safety reserve (256 tokens) plus `bytes/4` estimate; if the backend still rejects, treat as failure and retry.
28. The user dismisses before the main reply arrives → the bubble stays gone; the cycle already advanced.
29. The user never returns to the session → pending expires; the cycle's `base`/`from` already advanced; the next cycle starts at the next message.
30. The bubble and picker would overlap → the picker closes the bubble? No: the picker is above (z-index) and the bubble is repositioned below the picker? Design: opening the picker hides the bubble for the duration of the picker (fade out 120 ms) and restores it after close if still within 5 minutes; the timer keeps running.

## 16. Testing checklist (manual)

1. First message in a new session logs `bot` with `due = counter + x`, `150 <= x <= 300`.
2. Force `due` low (test hook) and send messages until due: one thought, text ≤350, no markdown, bubble above/below the avatar with tail pointing at it.
3. After the thought: `due = null`, `base` = counter at generation, `from` = last index; the next user message sets `due = base + x`.
4. Switch sessions during the 5 minutes: bubble reappears on return with less time; after 5 minutes it doesn't.
5. Reload in the window: bubble returns; after expiry: none.
6. `×` closes with the exit animation; other tabs hide it; it does not return.
7. Picker: choose each of the 8; header updates; other sessions unaffected; reopen shows the selected; switching sessions while open closes it.
8. Two sessions, both with due thoughts: each bubble appears only in its session.
9. Raw window: confirm user messages, tool calls and tool results are present; confirm summaries/view are absent; confirm the previous bubble text is absent.
10. Oversized window: trim from the top; newest user message retained; debug log records the trim.
11. Model error/empty: no bubble, same `due`, retry next message.
12. Reduced motion: no float/breath/stagger.
13. Accessibility: bubble announced; `×` reachable and labelled; picker focus trap; Escape.

## 17. Non-goals

- No global profile; no syncing the profile across sessions.
- No bubble history, no list of past thoughts, no notifications.
- No changes to the main agent's prompt, view, tree, compaction or billing.
- No per-avatar `x` ranges, probabilities or cooldowns.
- No advice call with tools, search, or file access.
- No sound on the bubble (the existing `open` sound is only for choosing a bot).
- No bubble in exports, shares, or the account page.
